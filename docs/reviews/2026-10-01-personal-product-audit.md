# EquityLens 个人使用产品审查（2026-10-01）

后续补测与推荐方案见 [个人使用补充全流程测试](2026-10-01-personal-product-full-validation.md)：包含生产启动、40个模块页面、40组问答、方案/建档/刷新/中断边界，新增F01—F13问题，以及待用户review的六个方案决策。两份文档互补，尚未执行修复。

## 结论

当前产品具备财务事实、分部、证据溯源和估值方案保存的基础，但还不适合宣称“个人用户可以完整、放心地日常使用”。首要问题是数据可信度和使用闭环，其次才是布局与视觉优化。

实际发现：同一公司总览与研究助手使用不同事实，助手证据在当前正式版本下返回 404；NVDA/KO/COST 护城河接口返回 500；三年财务表只收到四条事实；估值启用后丢失事实来源元数据；手机无法切换公司和研究模块。自动化测试全部通过，并不能排除这些真实使用问题。

本轮交付为审查记录与待办，未修改业务代码、发布数据或产品方案。历史建档任务完成不等于整个平台通过本轮产品验收。

## 已确认代码问题与修复待办

严重度：P0 为事实可信度破坏；P1 为核心流程失败或明确误导；P2 为明显体验/可访问性问题。下面均为待处理，不代表已修复。

### B01 · P0 · 已发布数据与研究读取分裂

- **证据**：NVDA 总览 TTM OCF 为 `125,648,000,000`，助手回答约 `$103B`；AAPL 总览为 `135,472,000,000`，助手约 `$147B`。MSFT 即使数值相同，返回的八个证据仍全部 404。
- **复现**：公司总览 → 看现金流快照 → 研究助手 →“现金流和回购情况？”→ 点证据。
- **原因**：`api/routes.py` 的 `management/risks/moat/research/promises` 虽解析发布上下文，下游 `domain/*` 与 `research/engine.py` 仍直接建立 `MetricEngine(store)`，分部读取也未传已发布 rows/config。返回 publication_id 不代表计算真的使用该发布版本。
- **修改**：建立统一的版本化研究读取入口；向所有下游传事实、分部配置和证据身份。前端模块请求也传当前 security/publication，避免后台发布变更后一个页面混用版本。
- **验收**：五家公司相同指标、期间、公式在总览/财务/助手/风险/治理一致；助手与风险每个数字证据在返回 publication 下解析成功；另测历史发布与发布切换。
- [ ] 完成数据读取统一与真实跨模块回归。

### B02 · P1 · 缺分部数据时护城河直接 500

- **证据**：NVDA、KO、COST `/moat` 均 500；日志定位 `domain/moat.py:179`，`UnboundLocalError: gaps`。
- **原因**：缺分部时先 `gaps.append(...)`，直到第 197 行才初始化 gaps。AAPL/MSFT 有旧分部配置，所以没有进入失败分支。
- **修改**：先初始化缺口列表，再逐模块添加；已完成信号保留，缺分部显示缺口。同时修复 B01，不把真实分部存在误判为不存在。
- **验收**：新公司、没有分部/没有董事会、分部解析失败三种边界均返回完整结构，不 500。
- [ ] 修复并加入无分部数据的接口回归。

### B03 · P1 · “三年财务表”只请求四条事实，且单元格不能溯源

- **证据**：`FinancialsSection.tsx` 请求六个指标、`annual&limit=4`；后端 facts 的 limit 是所有指标合计行数。NVDA 返回 FY2026 的四行，现金流/CapEx 空；MSFT/KO/COST 同样只拿到一个年度的部分行。
- **修改**：明确 API 的按指标/按期间截断契约，取最近三个完整年度；每个单元格绑定实际 fact/result 和来源入口。当前表格仅输出文本，却承诺“每行均可溯源”。
- **验收**：有足够数据时显示三年度×六指标；真实未披露保留原因；每个有值的单元格可打开来源。
- [ ] 修复事实请求与财务表溯源。

### B04 · P1 · KPI 静默混用不同期间，页面没有提示

- **证据**：NVDA 收入 TTM 截至 FY2027Q2，OCF/FCF 截至 Q1，净债务来自 FY2026Q3；AAPL 收入截至 FY2026Q3，但 OCF/FCF 截至 Q1。MSFT 工具条显示最新 FY2026Q3，收入 TTM 已到 Q4。
- **另一个复现**：KO 总览 TTM FCF 缺失，财务卡却显示历史完整窗口 `$12.6B`。后者取 `compute(...ttm)` 最后一条可算窗口，与总览 `current(...)` 的缺失语义不同。
- **原因**：指标各自以依赖事实最新季度为锚点；latest_period 只选直接 Q_STANDALONE，漏掉年度推导 Q4；UI 将它们统一称作“最近季度/TTM”，没有展示实际截止期。
- **修改**：保留合法历史数据，但每张卡显式显示实际期间与是否落后当前财报；当前窗口缺输入时展示缺失原因，不用旧窗口冒充当前值；统一 Q4/latest_period 定义。
- **验收**：上述公司跨期情况有明确标识；总览与财务对同一“当前 TTM”一致。
- [ ] 统一指标时点契约与页面标识。

### B05 · P1 · 估值确认后丢失事实来源与假设解释 · 已修复

- **证据**：NVDA 确认前有版本化默认理由；确认后页面出现“未标注期间”“净现金：未标注”“未标注版本”，无风险利率为 `—`，模型质量仍显示“完整（全部来自 SEC 事实）”。
- **原因**：`valuation/service.py:confirmed_valuation` 将所有输入 metadata 重建为 `user_confirmation`，持久化 `source_fact_ids: {}`。研究判断与 SEC 派生基准被同一标签覆盖。
- **修改**：确认记录保存完整事实基准来源/期间和默认假设理由，仅将用户审核/修改字段标为用户判断；质量说明根据真实事实与假设覆盖生成。
- **验收**：确认前后收入/股数/净现金的期间和来源可查；保存运行能复核原事实；不得将预测假设称作“全部来自 SEC”。
- [x] 保留确认后的完整估值元数据与真实质量标签。确认记录持久化完整基线bundle，确认后及保存run仍保留事实期间、来源、默认理由与source fact IDs；个人修改字段单独标记为用户覆盖。

### B06 · P1 · 估值滑杆范围不支持已审核的 NVDA 值 · 已修复

- **证据**：实际默认首年增长 30%、终期利润率 60.88%；正式估值页 `growth-slider max=20/value=20`，旁边显示 30%；`margin-slider max=60/value=60`，旁边显示 60.9%。
- **原因**：`ValuationSection.tsx` 固定 RNG 上限和步长，浏览器把超范围/不对齐值自动夹到可用值，React 草稿仍保留原值。
- **修改**：使用经审核的公司范围或允许精确数字输入；滑杆、文本、提交值统一。新手提示还写“四个滑杆”，实际为五个。
- **验收**：30%/60.88% 等初始值无静默截断；小幅操作不突然大幅改变假设；键盘值、文本和请求完全一致。
- [x] 修复参数范围、精度和说明。五项控件使用自适应范围并提供精确数字输入；NVDA 60.8816%利润率在数据副本和浏览器中保持原值，不再被旧60%上限夹断。

### B07 · P1 · 缺失不应输出判断，拆股不应判为稀释

- **证据 A**：KO 净债务 `—`，总览却显示“净负债状态”；`OverviewSection.tsx` null 落入净负债分支。
- **证据 B**：NVDA 治理页显示“5 年稀释股本 +867.0% / 正数=被稀释”。底层年度 shares 从 FY2022 `2.535B` 到 FY2026 `24.514B`，直接相除；代码未确认拆股可比口径。
- **修改**：null 显示无法判断；股票拆分/反向拆分和财报重述口径未验证时不生成稀释结论。明确开始/结束财年，CAGR 按实际年份跨度计算。
- **验收**：缺债务不推断负债；不同股数口径不会形成“被稀释”警告；年度缺口不冒充连续五年。
- [ ] 修复空值结论与股数可比性门禁。

### B08 · P1 · 过期行情被显示为未同步

- **证据**：AAPL 新鲜度提示 Nasdaq `$334.96`、09-18 观察且过期；Hero 仍显示“行情未同步”。MSFT 同样有 `$492.40`、09-16 快照却显示未同步。
- **原因**：Hero 和部分财务卡仅在 `market.status === "OK"` 时读取 quote，把已存在但过期的观察丢弃。
- **修改**：分别呈现“无快照/过期快照/最新快照/读取失败”；展示历史价格和观察时点，并保持价格对比不可用门禁。
- **验收**：过期快照不会被当成从未同步；顶部、财务、估值、新鲜度语义一致。
- [ ] 统一行情状态展示。

### B09 · P1 · 新标准发布与刷新管线仍未衔接完整

- **代码证据**：`refresh/service.py` 财务刷新调用旧 companyfacts sync，分部调用旧 `SegmentConfigRegistry`；该 registry 只覆盖旧公司。刷新未创建/质量验证/审核新的 publication。
- **影响**：NVDA/KO/COST 业务页可读审核版分部，旧刷新逻辑却找不到映射；财务写入旧可变表，正式总览继续读旧封存 publication。“已更新”可能只代表旧来源身份变化，未代表正式研究事实更新。
- **本轮实测边界**：实际点击 KO 四模块刷新，观察进度和中途切换；治理后来已有 03-16 proxy 数据。该轮没有留存四模块最终响应，不能宣称已完整验证刷新成功。上面的管线判断有直接代码证据。
- **修改**：明确刷新财务资料如何进入候选新版本、何时需要审核、何时切换发布；分部复用发行人专属配置；区分“来源已抓取”和“正式事实已更新”。
- **验收**：对已发布新公司刷新不会报旧映射缺失；新事实必须经质量门禁；无更新/待审核/正式更新三种结果可区分。
- [ ] 设计并完成已发布公司数据更新闭环。

### B10 · P1 · 刷新状态只在页面内，离开流程可能遗留互斥租约

- **代码证据**：四模块由前端依次请求；只有末次 `operation_finished=true` 释放后端令牌。切公司使 requestSeq 失效并从循环 return，刷新页面则销毁循环，没有取消/释放接口；租约最多等 15 分钟。
- **实际观察**：切公司后进度被清空，用户不能从页面找回原公司刷新过程。后端 health 在长刷新期间仍可正常响应。
- **证据级别**：页面丢进度已实测；15 分钟残留租约为代码分支确定存在的风险，本轮未完整复现到超时释放。
- **修改**：用持久任务在后台完成整轮刷新，或实现明确的停止/释放与恢复机制；避免依赖某个标签页连续发送后续请求。
- **验收**：刷新中切公司、关标签、强制刷新后可找回状态；不用靠重启或等待租约过期才能继续。
- [ ] 补齐刷新生命周期与恢复测试。

## 测试覆盖为何没挡住这些问题

`apps/web/e2e/research-boundaries.spec.ts` 的问答与 evidence 使用可解析的 stub；它证明组件在理想接口下能展示来源，没有证明真实回答返回当前 publication 里的 ID。`tests/e2e/smoke.py` 假定首页是 Apple、估值直接可用，已经落后于当前公司目录和审核门禁。既有移动测试主要检查不溢出及建档入口，没有检查八个研究模块是否能访问。

后续必须增加真实已发布数据的端到端契约检查，且与组件拦截测试同时保留：

| 新增验收 | 核心断言 |
|---|---|
| 五公司跨模块一致性 | company/security/publication/期间/值一致；每个证据可解析 |
| 无旧表数据的新公司 | 只留封存 dataset 仍可打开研究；不会偷偷依赖旧 canonical/segment 表 |
| 三年度财务表 | 指标×年度完整、来源逐格可达，缺失有原因 |
| 指标滞后及年度 Q4 | 时点显示正确，旧窗口不可冒充当前窗口 |
| 估值确认→编辑→保存→重开 | 范围/精度不夹断；事实来源/假设理由完整；个人方案可复核 |
| 手机完整研究 | 公司选择与八模块均可访问，弹窗键盘可退出 |
| 新证券从识别到适配 | 提前说明需人工操作；暂停能恢复；证据向导可完成，仍执行质量门禁 |
| 已发布公司刷新 | 新资料进入审核/发布闭环，页面明确当前使用版本；中断能恢复 |
| 部分模块失败 | 信号与旧数据保留，缺失/错误/过期分开；无未处理 500 |

## 推荐实施顺序

1. **恢复数据可信度**：B01 → B02 → B03/B04 → B07/B08/B12。先统一发布读取，再修依赖它的计算和来源。
2. **完成估值及更新闭环**：B05/B06 → B09/B10，同时落实 D03 的能力提示。刷新后必须知道新数据在哪里、是否已进入研究版本。
3. **让个人能独立完成研究**：D01/D02 → B11/B13/B14 → D04/D05/D08。
4. **增强日常积累和维护**：D06/D07/D09/D10。

每一批以真实数据副本中的用户流程验收，再补适量回归。批次完成后更新本报告的复选项与关联验证文档；不能仅凭测试计数标完成。
